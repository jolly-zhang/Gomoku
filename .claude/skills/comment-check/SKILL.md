# 注释检查技能

用于：检查代码注释质量，输出文字报告。**只报告，不修改代码。**

## 触发输入
- 默认检查 `src/` 下全部 `.ts` / `.tsx` 代码（UI 组件 + 核心逻辑 + 测试）。
- 可选带一个目标文件或目录，只检查指定范围。

## 三项检查
1. **缺失 / 密度**：每个函数、组件、关键逻辑块都应有注释（做什么、关键参数、为什么）；核心代码行应有行内注释。整体注释密度参考「10 行约 3 行注释」（≈30%，作为经验值，非硬性数行）。完全无注释的模块/函数、或核心逻辑无解释的，点名。
2. **匹配度**：注释必须和代码实际行为一致。抓出「注释说 A、代码做 B」的过期注释、张冠李戴、描述相反。
3. **小白可读**：注释应让不懂代码、不懂五子棋规则的人也能看懂。避免术语黑话；对领域词（禁手、活三/冲四/长连、落子预览等）或非显然逻辑，要解释清楚。

## 硬性约束
- 只报告，不修改任何代码。
- 范围限项目内 `src/`；排除 `node_modules`、`web-build`、`.expo`、`_legacy_swift`。

## 执行步骤
1. 读取目标文件（默认遍历 `src/**/*.ts`、`src/**/*.tsx`）。
2. 按上述三项逐文件检查。
3. 输出报告（固定格式）。

## 报告格式（固定）
```
注释检查报告
- 检查文件：N 个
- 问题总数：M（缺失 X / 不匹配 Y / 不友好 Z）
- 缺失：
  - [文件:行] 对象名 —— 缺什么（无函数注释 / 核心逻辑无行内注释）
- 不匹配：
  - [文件:行] 现有注释 —— 实际代码行为（为何不匹配）
- 不友好：
  - [文件:行] 现有注释 —— 小白难懂之处 + 建议改法
- 结论：一段话总结整体注释质量与优先修复项
```

## 成功标准
- 报告按固定格式输出；
- 每个问题能定位到「文件:行」，并给出具体原因与建议；
- 对注释良好的文件，在结论中如实说明，不强行挑刺。
